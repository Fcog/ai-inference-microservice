# 🔒 GitOps Secrets Infrastructure (Vault & External Secrets Operator)

This directory documents the zero-trust runtime configuration and secrets management setup. Instead of hardcoding API keys or storing encrypted secrets inside a Git repository, this project decouples secrets entirely by bridging an enterprise-grade **HashiCorp Vault** instance with native Kubernetes secrets using the **External Secrets Operator (ESO)**.

---

## 🏗️ Secrets Handshake Architecture

```text
┌──────────────────────┐             1. Reads Keys
│ HashiCorp Vault Pod  │◄─────────────────────────────────┐
│ (secret/ai-service)  │                                  │
└──────────────────────┘                                  │
                                                ┌─────────┴──────────┐
                                                │  External Secrets  │
                                                │   Operator (ESO)   │
                                                └─────────┬──────────┘
                                                          │
                                                          │ 2. Dynamically Generates
                                                          ▼
                                                ┌────────────────────┐
                                                │ Native K8s Secret  │
                                                │(ai-app-runtime-sec)│
                                                └─────────┬──────────┘
                                                          │
                                                          │ 3. Binds Env Var
                                                          ▼
                                                ┌────────────────────┐
                                                │  Application Pod   │
                                                │(process.env.OPENAI)│
                                                └────────────────────┘
```

1. **Vault Engine:** Acts as the centralized system of record for all infrastructure passwords, tokens, and corporate variables.
2. **External Secrets Operator (ESO):** Continually polls the external Vault server, retrieves values securely, and dynamically writes them into native, local Kubernetes secrets.
3. **Application Decoupling:** The Node.js application remains standard and unaware of Vault; it simply inherits standard environment flags natively from the Kubernetes Secret generated by ESO on cluster startup.

## 🚀 Infrastructure Bootstrap Steps

Follow these execution loops to provision the Vault server and configure the sync engine on your local cluster.

### 1. Install the External Secrets Operator (ESO)

```bash
# Add the official ESO Helm Repository
helm repo add external-secrets https://external-secrets.io
helm repo update

# Install the operator stack into a dedicated namespace
helm install external-secrets external-secrets/external-secrets \
  --namespace external-secrets \
  --create-namespace
```

### 2. Provision HashiCorp Vault in Local Development Mode

Run Vault in dev mode to automatically unseal the database instance in-memory with a static configuration root token (`root`):

```bash
# Add the HashiCorp Helm Repository
helm repo add hashicorp https://hashicorp.com
helm repo update

# Deploy Vault into its own dedicated namespace
helm install vault hashicorp/vault \
  --namespace vault \
  --set "server.dev.enabled=true" \
  --set "server.dev.devRootToken=root" \
  --set "server.extraArgs=-dev-listen-address=0.0.0.0:8200" \
  --wait
```

### 3. Seed Your Application Credentials into Vault

Open an active terminal execution shell inside the Vault container to initialize the Key-Value (KV) version 2 engine and inject your credentials:

```bash
# 1. Execute into the running Vault container pod
kubectl exec -it vault-0 -n vault -- /bin/sh

# 2. Login to the internal CLI controller using the root token
vault login root

# 3. Enable the Key-Value (KV) version 2 secrets framework engine
vault secrets enable -path=secret kv-v2

# 4. Insert your secure parameters into the storage engine path
vault kv put secret/ai-service-credentials \
  api_key="sk-mock-1234567890abcdef" \
  redis_pass="my-secure-redis-password"

# 5. Terminate the container session
exit
```

### 4. Provide ESO with Access Credentials

Create a basic Kubernetes secret containing the Vault root token so that the operator can authenticate and establish its network handshake securely:

```bash
kubectl create secret generic vault-token \
  --namespace default \
  --from-literal=token="root"
```

## 🔄 Dynamic Variable Modifications & Rotations

When an API token or credential rotates, **do not touch your Git repository or modify code.** Instead, update the parameters directly inside Vault.

### 1. Update Keys inside Vault

```bash
# Exec back into the container and apply the updated payload block
kubectl exec -it vault-0 -n vault -- /bin/sh
vault login root

# Overwrite the path with the updated variable parameters
vault kv put secret/ai-service-credentials \
  api_key="sk-NEW-UPDATED-KEY-67890" \
  redis_pass="my-secure-redis-password"
exit
```

### 2. Verify Synchronized State Output

Because your `external-secret.yaml` template manifest is configured with a quick `refreshInterval: "10s"`, the operator will update the target secret automatically within ten seconds. Verify the updated secret payload using the decoding utility string:

```bash
# Decode the native secret output to inspect configuration delivery
kubectl get secret ai-app-runtime-secrets -o jsonpath="{.data.OPENAI_API_KEY}" | base64 --decode
```

### 3. Trigger a Zero-Downtime Rolling Restarter

While Kubernetes modifies the target secret instantly, active running pods require a refresh to absorb updated environment buffers. Issue a rolling restart to force the nodes to pull fresh configuration values with zero service downtime:

```bash
kubectl rollout restart deployment/my-ai-app-deployment
```
